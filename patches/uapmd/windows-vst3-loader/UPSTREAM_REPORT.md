# 上流向け報告文（草稿・未送信）

報告状態: **未報告**。報告後は、補修の [説明書](README.md) に課題またはプルリクエストのリンクを記録する。

## 件名

Windows の VST3 ローダーがプラグイン本体の代わりに cacert.pem を選択することがある

## 発生した現象

Windows x64 で cat-plugin-player が起動時にインストール済みの VST3 プラグインを探索すると、Windows の「正しくないイメージ」ダイアログが表示されました。ダイアログには次のファイルとエラーコードが示されました。

- 対象ファイル: `Reason Rack Plugin.vst3/Contents/x86_64-win/cacert.pem`
- エラー状態: `0xc000012f`

Reason Rack Plugin のバンドルには、本体の `Reason Rack Plugin.vst3` とともに、証明書、フォント、テキストファイル、サブディレクトリが含まれています。

調査・検証した UAPMD のリビジョンは `bc39b50faf2f2b02668de82d3d95f2bdbafd3c34` です。2026-10-07 の文書更新時にも、使用中の依存ソースがこのリビジョンであり、対象ファイルに Git の差分がないことを確認しました。対象ソースの SHA256 は `2354fe27eec1c1a40b20dc5ce52da54af9c7b3f4b075850b1bd807851bb62e7c` です。

## 原因

`source/remidy/src/vst3/ClassModuleInfo.cpp` の `remidy_vst3::getPluginCodeFile()` は、ファイルの種類や拡張子を確認せず、`std::filesystem::directory_iterator(binDir)` が最初に列挙した項目を返します。

`loadModuleFromVst3Path()` は、そのパスを `loadLibraryFromBinary()` に渡します。Windows では `LoadLibraryW()` で読み込むため、最初の項目が `cacert.pem` であると、プラグイン本体ではなく証明書をライブラリとして読み込もうとします。ディレクトリの列挙順から、どの項目がプラグイン本体かを判断することはできません。

## 再現手順

1. Windows x64 に Reason Rack Plugin の VST3 をインストールします。
2. remidy を使い、`loadModuleFromVst3Path()` を呼ぶ経路でバンドルを探索または読み込みます。`moduleinfo.json` を読むだけの経路では、この読み込み処理を確認できません。
3. ABI ディレクトリで最初に列挙された項目が `cacert.pem` である場合、本体が読み込まれず、「正しくないイメージ」ダイアログが表示されます。ほかのリソースやディレクトリが選ばれても、読み込みに失敗する可能性があります。

ファイル選択処理の最小回帰テストには、`.vst3` バンドルのディレクトリ内に `Contents/x86_64-win/cacert.pem` と `Contents/x86_64-win/<バンドル名>.vst3` を用意するだけで足ります。選択処理が後者を返すことの確認には、製品の実バイナリは不要です。このテストはパスの選択を検証するもので、バイナリの読み込みや初期化は検証しません。

## 修正案と現在のローカル補修

Windows では、通常ファイルで拡張子が `.vst3` のものを対象とし、次の規則で選択することを提案します。cat-plugin-player のローカル補修では、この規則を実装しています。

1. バンドルと同名の `.vst3` ファイルを優先します。
2. 同名ファイルがなければ、ABI ディレクトリ内に `.vst3` の通常ファイルが一つだけある場合に採用します。これにより、バンドル名が変更された場合も、本体が一意なら読み込めます。
3. 候補がない場合、同名ファイルがなく候補が複数ある場合、列挙中にエラーが発生した場合は、空のパスを返して読み込みを行いません。
4. 拡張子の大文字小文字は区別せず、ディレクトリ、証明書、フォント、補助 DLL を候補から除外します。
5. 単一ファイル形式の VST3 にも、通常ファイルであることと `.vst3` 拡張子の検証を適用します。

macOS と Linux は配置や命名規則が異なるため、各プラットフォームのバイナリ選択処理を維持してください。現在のローカル補修は Windows にのみ適用し、Reason 固有の製品名判定は行っていません。バイナリ自体の破損やプラグイン固有の初期化エラーは、この補修の対象外です。

補修済みローダーと cat-plugin-player のカテゴリ取得処理は、同じ選択ヘルパーを使用します。Windows の CMake 構成時に上流ソースの適用条件を確認し、`target/shim/generated/windows-vst3-loader/ClassModuleInfo.cpp` に補修済みコピーを生成して、remidy のコンパイル対象を差し替えます。UAPMD の依存ソースは直接書き換えません。

同じ適用条件を満たす依存ソースを取得し直した場合も、構成時に再適用されます。想定したコードやソース一覧が変わった場合は、対象ファイル、失敗条件、取得可能な上流リビジョンなどを表示して停止します。上流での修正を確認し、使用する UAPMD に取り込まれた状態で回帰検証を行った後、この一時補修を撤去したいと考えています。

## ローカル補修の検証結果

以下は、2026-10-06 に Windows x64 と上記リビジョンで実施した検証の記録です。今回の文書更新では、実装と記録の照合および依存ソースのリビジョン・差分・ハッシュの確認を行い、ビルドや実機検証は再実行していません。

- コンパイル済み remidy の選択処理が、インストール済みの Reason バンドルから `Reason Rack Plugin.vst3` 本体を選び、`cacert.pem` やほかのリソースを選ばないことを確認しました。
- 二回のカタログ探索で、どちらも Reason バンドルの詳細探索を実行し、22 プラグインの中に Reason Rack Plugin（音源）と Reason Rack Plugin Effect（エフェクト）の両方が含まれることを確認しました。報告対象の「正しくないイメージ」ダイアログで停止せず完了しました。
- バイナリ選択の回帰テストでは、リソースファイル、ディレクトリ、候補の欠落・曖昧さ、バンドル名の変更、大文字の拡張子を検証しました。単一ファイル形式についても、コンパイル済み remidy が `.vst3` 本体を受け入れ、証明書を拒否することを確認しました。
- 補修適用の回帰テストでは、二つの新しい模擬依存ディレクトリへの適用、再適用結果の一致、入力ソースの非変更を確認しました。上流コードの変更、対象コードの重複、ヘッダー参照の変更、対象ソースの欠落について、診断を伴って停止することも確認しました。
- リリースビルド、Rust の整形確認、Clippy の検査に成功しました。補修ディレクトリの7ファイルが Cargo の配布対象に含まれることも確認しました。

フルビルドには既存の依存キャッシュを使用しました。模擬依存ディレクトリからの補修再適用は検証しましたが、依存全体を新規取得した環境でのフルビルドは未検証です。また、カタログ探索は既存キャッシュを使用しており、未登録プラグインの新規探索全体を検証したものではありません。

最初のビルドでは、既存 ImTimeline キャッシュに UAPMD の `external/patches/imtimeline.patch` を二重適用する構成処理の問題で停止しました。ログ・設定・差分を確認し、依存ソースの差分全体が当該パッチと完全一致して逆適用可能であることを確認したうえで、そのパッチだけを逆適用し、既存手順で再適用してビルドに成功しました。追加のビルド設定変更や検証の省略は行っていません。依存ソースは元のパッチ適用済み状態に戻り、失敗時の `.rej` ファイル四つは削除済みです。

補修の適用条件、検証コマンド、適用失敗時の調査手順、上流修正後の撤去条件は、補修の [説明書](README.md) に記録しています。
