# ADR 0008: Surge XTの初音待ちと、catalog音色ごとの待ち省略

状態: 採用。未判定は暫定100ms、判定表で許可したCLAP catalog音色は0ms。

## 根拠

Surge XTだけ最初のnote onが無音になる場合があるというユーザー報告。
既存の自動演奏は最初の音声ブロックからnote onを送信する。
既存のSurge XT実機テストでは、復元stateが音声処理を開始してから適用されることを確認している。
state反映と最初のnote onの競合が原因という仮説であり、必要な最小待機時間は未確定。

## 当初の決定

`src/plugin_specific/surge_xt.rs`で100msの開始待機を指定する。
対象はCLAP `org.surge-synth-team.surge-xt`とVST3 `ABCDEF019182FAEB566D624153675854`の組だけ。
名前、vendor、パスで識別しない。その他のプラグインは待機なし。

音声ストリーム開始から100ms分のサンプルを処理し、待機中も空のイベントでプラグインを処理する。
UIと音声スレッドでsleepしない。待機をまたぐブロックではJR Timestampで最初のnote onの位置を指定する。
最初の音を省略せず、フレーズ全体の開始を遅らせる。
新規ロード、Favorite・セッション復元、音声ストリーム再構築時に同じ待機を適用する。
演奏停止中も待機時間は経過し、同じストリームでの演奏パターン切替・再開には待機を繰り返さない。
Surge XTをエフェクトとして接続した場合は、主音源の開始待機に影響させない。

## 当初の検証と調整

製品ID限定、44.1/48kHzと64/256/1024フレームで最初のノートと次のノートの位置、停止中の経過とパターン切替を回帰テストする。
100msを必要最小値や無音の完全解消を実測した値として扱わない。
実機で新規インスタンスに保存stateを復元し、48kHz・256フレーム・壁時計に合わせた音声処理で各待機時間を3回比較した。
`cargo test native_first_note_settling_measurement -- --ignored --nocapture`で再計測できる。
ユーザーのFavoriteを読み取り専用で使用し、保存・変更はしない。

|形式・音色|待機0ms|25ms|50ms|100ms|
|---|---|---|---|---|
|CLAP・Surge XT 2|3/3、0.458ms|3/3、24.792ms|3/3、50.125ms|3/3、100.125ms|
|VST3・auto Surge XT 3|3/3、0.417ms|3/3、25.354〜25.375ms|3/3、50.021〜50.042ms|3/3、100.021〜100.063ms|

時間は処理開始から絶対値1e-6を超える出力サンプルまで。物理出力の遅延ではない。
CLAPの出力開始は内部処理の粒度等でnote on指定時刻と一致しない場合がある。
今回の条件では無音症状は再現せず、100msの十分性・最小値は証明できないため暫定値を維持する。
VST3では各復元時に`failed to set controller component state: -2147467263`の上流ログが出た。
ホストのload_stateは成功し発音は確認できたが、controller stateの完全復元は未確認。この依存側問題は今回変更していない。
実際のアプリ起動・Favorite切替・多様な音色で繰り返し確認し、必要なら待機時間を調整する。
遅いアタックの音色による無音とnote on消失を区別する。
上流のstate反映手順の改善などで待機不要と確認できたら撤去する。

## catalog全体の一次選別へ切り替えた理由

目的は、patch browserで音色を変更してから鳴るまでのUXを改善し、前回の音色を復元する起動でも初音までの時間を最小化することである。
PCMの完全一致を求める調査では同条件でも一致しない音色が多かったが、波形の不一致だけでは実用上の不合格を意味しない。
少数音色の詳細な反復や未計測を大量に残す進め方ではこの用途に答えられないため、対象をsaved stateからSurge XT CLAPのcatalog全体に変更し、VST3を除き、開始位置だけを各条件1回で比較する一次選別を選んだ。

新規process・新規instanceに同一stateを読み込み、発音前に100msまたは10ms分の空イベントを処理してから、note on後200msを高速オフラインで収録した。
待ちは音声サンプル時間であり、実時計のsleepではない。48kHz・256frames、note48・velocity100・CC1=0、追加effectなしで、
stereo powerの中央寄せ1ms移動RMSが記録内最大値の1%に達する位置を、note on基準で比較した。PCMの一致・音量・音色全体の一致や反復再現性は判定しない。

catalogの3,171音色を一巡し、開始位置の差が5ms以内は3,045、5ms超は110、片方または両方の記録が全サンプル0は14、エラーは2だった。
差が1ms以内は2,561、1ms超2ms以内は246、2ms超5ms以内は238。2,561は5ms以内の候補の84.1%、catalog全体の80.8%である。
エラーはFXP chunk長の検証失敗1件と100ms条件の30秒timeout1件で、無音・エラーを音色の不安定さと断定しない。
数値は[配布用の全計測値と判定表](../../../cat-music-patterns/surge-xt-start-delay.json)に保存する。

## 0ms採用は実測事実と区別する

ユーザーは、このうち差が1ms以内の2,561音色について、0msで鳴らしてよいと判断し、不具合の可能性を引き受けて実際のUXで検証する方針を明示した。
10msと100msの比較は0msの成功を証明していない。100msとの比較も絶対的な正しさの証明ではない。
全音色での厳密な保証より、音色変更と起動の体感を改善することを優先し、今回は0msの追加計測を採用の前提にしない。
無音、エラー、未掲載、許可対象外の音色は100msを維持する。VST3、任意のsaved state、Favoritesへこの判定を広げない。

今後条件を見直せるよう、計測をこのアプリの専用CLIとして再実行可能にし、計測値と0msの採用判断を分けて保存する。
閾値のみの変更では保存した全音色の計測値から再選定でき、比較待ちを0msなどへ変更したい場合は再レンダリングする。
アプリ側に1msや音色一覧を固定せず、CLIが出力した判定表を情報源にする。
CLIは `measure-surge-start-delay` で、閾値だけの再選定は `--reclassify` を使う。出力した表のcat-music-patternsへのcommit・pushは人間が行う。

## 配布と現在の音色への結び付け

判定表は兄弟repoのcat-music-patternsに置き、GitHubから取得してLocal AppDataのconfigディレクトリ内に保持する。
初回起動の短縮のための同梱はユーザーが不要と判断し、simpleさを優先して採らない。ローカル表がない間は100msとし、通信を発音開始の前提にしない。
背景更新に失敗しても以前の有効な表を保持し、更新のために演奏中の音源を再起動しない。

起動時に読むstatusには、現在の音色の許可をplugin・patch・stateハッシュ・判定表の版に結び付けて保存する。
音色変更の失敗では以前の判定に戻し、別音色や変更されたstateに古い0ms許可を流用しない。
プラグインGUI内の編集は追跡できないため、GUIを開いたinstanceは許可対象から外す。GUIを閉じ、ブラウザーから既知の音色を適用し直した場合は改めて判定できる。
既存statusに許可情報がない場合も音色・設定をそのまま復元し、待ちだけ従来の100msとする。既存stateやFavoritesの移行・一括再保存は必要としない。
