# ADR 0008: Surge XTの最初の自動note onを遅延する

状態: 採用（100msは暫定値）

## 根拠

Surge XTだけ最初のnote onが無音になる場合があるというユーザー報告。
既存の自動演奏は最初の音声ブロックからnote onを送信する。
既存のSurge XT実機テストでは、復元stateが音声処理を開始してから適用されることを確認している。
state反映と最初のnote onの競合が原因という仮説であり、必要な最小待機時間は未確定。

## 決定

`src/plugin_specific/surge_xt.rs`で100msの開始待機を指定する。
対象はCLAP `org.surge-synth-team.surge-xt`とVST3 `ABCDEF019182FAEB566D624153675854`の組だけ。
名前、vendor、パスで識別しない。その他のプラグインは待機なし。

音声ストリーム開始から100ms分のサンプルを処理し、待機中も空のイベントでプラグインを処理する。
UIと音声スレッドでsleepしない。待機をまたぐブロックではJR Timestampで最初のnote onの位置を指定する。
最初の音を省略せず、フレーズ全体の開始を遅らせる。
新規ロード、Favorite・セッション復元、音声ストリーム再構築時に同じ待機を適用する。
演奏停止中も待機時間は経過し、同じストリームでの演奏パターン切替・再開には待機を繰り返さない。
Surge XTをエフェクトとして接続した場合は、主音源の開始待機に影響させない。

## 検証と調整

製品ID限定、44.1/48kHzと64/256/1024フレームで最初のノートと次のノートの位置、停止中の経過とパターン切替を回帰テストする。
100msを必要最小値や無音の完全解消を実測した値として扱わない。
実機で新規インスタンスに保存stateを復元し、48kHz・256フレーム・壁時計に合わせた音声処理で各待機時間を3回比較した。
`cargo test native_first_note_settling_measurement -- --ignored --nocapture`で再計測できる。
ユーザーのFavoriteを読み取り専用で使用し、保存・変更はしない。

|形式・音色|待機0ms|25ms|50ms|100ms|
|---|---|---|---|---|
|CLAP・Surge XT 2|3/3、0.458ms|3/3、24.792ms|3/3、50.125ms|3/3、100.125ms|
|VST3・auto Surge XT 3|3/3、0.417ms|3/3、25.354〜25.375ms|3/3、50.021〜50.042ms|3/3、100.021〜100.063ms|

時間は処理開始から絶対値1e-6を超える出力サンプルまで。物理出力の遅延ではない。
CLAPの出力開始は内部処理の粒度等でnote on指定時刻と一致しない場合がある。
今回の条件では無音症状は再現せず、100msの十分性・最小値は証明できないため暫定値を維持する。
VST3では各復元時に`failed to set controller component state: -2147467263`の上流ログが出た。
ホストのload_stateは成功し発音は確認できたが、controller stateの完全復元は未確認。この依存側問題は今回変更していない。
実際のアプリ起動・Favorite切替・多様な音色で繰り返し確認し、必要なら待機時間を調整する。
遅いアタックの音色による無音とnote on消失を区別する。
上流のstate反映手順の改善などで待機不要と確認できたら撤去する。

## ビルド検証

- 通常テスト82件、実機計測1件、`cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`成功。
- `cargo build --release`成功。初回は実行中の既定targetのexeによるファイルロックで停止したが、ユーザーがアプリを終了した後、設定変更なしで再実行して成功した。
- 既定targetと既存依存キャッシュを使用。試行用設定・別targetディレクトリは作成していない。新規環境での再現性は未確認。
